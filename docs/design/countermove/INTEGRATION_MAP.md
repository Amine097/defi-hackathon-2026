# Countermove · frontend / backend integration map

_Audit of `work/frontend-redesign` @ `2a77f03`, 10 Oct 2026. Source spec: `docs/FAULTLINE_Countermove_v3_Autonomous_Crisis_Response.md`._

## 1. What exists in the backend today

There is **no Countermove backend**. A search of the repository (all branches) finds no RescueVault contract, no `.sol` file, no keeper or watcher, no executor, no Countermove endpoint, schema, test or fixture. The v3 document is a specification; `docs/FAULTLINE_COUNTERMOVE_TECHNICAL_AUDIT.md` audits reusable read-side code only.

| Capability | Status | Where |
|---|---|---|
| Dependency graph, propagation, scenarios, verdict | Implemented | `GET /api/analyze` → `src/defirisk/api_payload.py` |
| Morpho borrower read: debt, collateral, LLTV, health factor, liquidation buffer, price grid | Implemented (read only) | `GET /api/analyze?borrower=0x…|auto` → `liquidation` block (`leverage.py`, `morpho.py`) |
| Vault analyzer | Implemented | `GET /api/vault` |
| Borrower decision | HOLD vs sell all collateral only. No partial repay, no top-up | `leverage.py:_borrower_decision` |
| Rescue policy, reserves, authorization, spending limits | **Not implemented** | — |
| Watcher / crisis detection states | **Not implemented** | — |
| Strategy comparison (repay / top-up / no action) | **Not implemented** | — |
| Executor, transactions, receipts, fork proof | **Not implemented** | — |

## 3. Missing contracts (each one the UI names when it is needed)

Defined once in `public/assets/js/countermove/adapters.js` (`MISSING`). The live adapter returns `unavailable` for all of them and never falls back to a fixture.

| Contract | What the frontend needs |
|---|---|
| Rescue policy read / save / validate | allowed actions, reserves, per-event caps, trigger, required buffer, as accepted by the backend or the vault |
| Arm / disarm / revoke | an accepted authorization with its on-chain reference and the limits enforced |
| Reserve balances | loan-token and collateral balances actually held by the vault |
| Watcher status and current crisis | trigger node, evaluated scenarios, state with block or timestamp |
| Strategy comparison | per strategy: feasible, amount, post-action buffer, reserve after, rejection reason; selected strategy and reason |
| Execution result and receipt | environment, chain id, tx hash, receipt status, block number, pre/post position re-read on chain, reserves consumed |

No field names are proposed as a backend schema. The demo fixtures use a frontend-only shape (`faultline.countermove.demo/0`) that must be re-mapped in one place (the adapter) when the real contract exists.

## 4. Demo fixtures

`public/data/countermove/demo-{repay,topup,no_action,reverted}.json`, generated by `docs/design/countermove/build_demo_fixtures.py`.

- Numbers come from the spec's own formula (section 4): `B_s = LLTV·(V_s + q_s) − (D − r)`. The generator first reproduces the spec's worked example (repay 460, top-up 594.32) and refuses to write if it does not match.
- LLTV 91.5% is the real parameter of the market in the saved run. Debt, collateral, reserves and limits are invented and labelled as such.
- The trigger node (`feed`) is a real node of the saved graph; the propagation path and percentages shown are computed by the production `cascade()`.
- Every fixture has `demo: true`, `environment: "demo"`, and no hash, block or receipt.

## 5. Evidence rule

`verifyExecution()` in `adapters.js` is the only place that decides what may be claimed.

- **CONFIRMED** requires all five: a verified environment (fork, testnet or mainnet), a 32-byte transaction hash, a receipt with success status, a block number, and a post-action re-read of the position. The environment is always shown with it.
- A demo fixture that records success is shown as **SIMULATED**. A non-demo run with incomplete evidence is **UNVERIFIED**.
- Covered by `tests/js/countermove_evidence.test.mjs` (10 tests).
